Settings, Appflare updates has a Versions list: the newest versions of the manager's own Worker, each with the Appflare version it runs and what made it, the serving one marked. Admins, the owner included, can roll back to an older one after typing its version. The rollback runs in the request and is recorded under Jobs as an Appflare rollback with its log. Before it switches, the older version must answer at its preview URL as the Appflare version it was deployed with and with a working database, and its code must know every migration the database has: the database is not rolled back, so a version older than the database's schema is refused, using the same comparison as the home page's downgrade banner. `/api/health` now reports `knownSchemaVersion` for that check; versions that do not report it are refused. The deployment is never forced, so Cloudflare's refusal of a version whose secrets changed since (an older API token or auth secret) is passed on. No other job runs meanwhile, the rollback turns automatic updates of Appflare off so the cron does not move forward again, and the page follows the switch and reloads onto the older version. Usage data records such a job by its kind only.
