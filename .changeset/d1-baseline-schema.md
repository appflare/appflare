Catalog manifests can give a D1 binding a baseline: `resources.d1[binding].baseline` names one SQL file that holds the database's whole current schema, for apps whose migrations only bring older databases up to date (ALTERs that fail on an empty one). It runs once, on a new database, before the migrations, and every migration the version ships is recorded in `d1_migrations` as applied without running. A baseline may create without IF NOT EXISTS and insert rows; `baselineFileProblems` refuses ATTACH, DETACH, DROP DATABASE, a PRAGMA that sets a value (except `defer_foreign_keys`), statements that open or end a transaction, any mention of `d1_migrations` or a `sqlite_` or `_cf_` table (in single quotes too), a file that ends inside an unclosed comment, string or quoted name, and a file that creates no table other than temporary ones. Seed statements are now also refused when they end inside an unclosed comment or string or name an internal table in single quotes (`unclosedAtEndProblem`). A binding cannot have both a baseline and schema files.

Artifacts carry the file as `d1Baseline`, one per binding, checked against the catalog manifest by `artifactD1Problems` and listed by `artifactD1Files`. `artifactFormatFor` gives format 5 for an artifact with a baseline, so a manager that reads only formats 1 to 4 refuses it instead of running the migrations on an empty database. `endsInsideStatement` tells whether SQL ends inside an unclosed statement. The sandbox Worker says it keeps baselines with the `d1-baseline` feature (`SANDBOX_FEATURE_D1_BASELINE`). The JSON Schema is regenerated.
