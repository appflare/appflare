Wildcard domains are set up more carefully. If Cloudflare stops part way (a missing permission, a route that already exists, an outage), Appflare removes the records and routes it had just added, including one whose answer was lost, and says so, instead of leaving them on the domain unrecorded; if it cannot remove some, the message names only what is left to delete. A failure that may pass, such as a short Cloudflare outage, is then tried again by the install, while a refusal is reported for the admin to fix. A hostname with names under it that already go through Cloudflare's proxy, such as `api.tunnels.example.com`, is refused with those names listed, since the app would take them over, unless the admin agreed to serve the whole domain; names that another app's custom domain or a more specific route already serves do not count. A route to the app's Worker that an admin made by hand is used but no longer deleted when the wildcard domain is removed. Assigning or removing a wildcard domain now redeploys the settings when any Worker of the app uses `{{wildcardHostname}}`, not only the main one, and an install whose wildcard domain could not be set up deploys its settings again so they do not name a hostname the app does not have (the jobs list shows that settings change as automatic).

Building in the sandbox Worker: an app that installs no packages (`install.installDirs: []`), an app with a multi-line secret, and a static site whose wrangler config has no `main` now get a plain "update the sandbox" message when the sandbox Worker is too old to build them, instead of failing inside the build or dropping the multi-line setting. Uploads now send the assets directory's `_redirects` and `_headers` rules that the packer records, and updating Appflare or the sandbox Worker refuses a release that has no Worker code instead of uploading it without a main module.
