Enable, update and disable sandbox builds from Settings > Account and capabilities. On an account where Workers Paid is detected, "Enable sandbox builds" runs a job that downloads the sandbox Worker release this Appflare version comes with, verifies its signed manifest, creates the `appflare-builds` bucket, uploads the sandbox Worker with its container classes and Durable Object migrations, turns its `workers.dev` URL off, creates the two container applications on the release's image, waits until their containers are up, and connects Appflare to it. Every step checks what is already there, so running it again continues a stopped run. The card names what blocks it first (R2 not enabled, or a token without Containers: Edit). When Appflare comes with a newer sandbox Worker than the one running, "Update sandbox" uploads it and rolls both container applications out to the new image. "Disable sandbox builds" asks for the sandbox Worker's name, is refused while an app built or deployed in it is installed, and then disconnects Appflare, force-deletes the sandbox Worker, deletes both container applications, and empties and deletes the bucket. The token template gains the optional Containers: Edit permission for this. "Remove Appflare from this account" now also deletes the sandbox Worker's two container applications when the token has Containers: Edit, and only asks you to delete them by hand when it lacks it.

Connecting sandbox builds now decides whether Appflare is already connected from the version that serves traffic instead of the newest uploaded one, so connecting again after a failed preview check works instead of reporting it as done.
