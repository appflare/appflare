Protection with Cloudflare Access can now be turned on or off for an installed app, and follows the catalog's `access` block.

- Turning it on or off runs the app's settings change job with the protection change inside it. On: the app is protected first (under the Access lock, covering its external domains too), then its settings that use the Access placeholders are deployed again with the new audience tag and team domain. Off: the settings are deployed again first with those values empty, so an app that checks them turns everyone away rather than trusting a request, then the protection is removed. The job ends with a health check. Turning it off is refused for an app whose catalog entry requires protection.
- An app whose entry requires protection is protected at install without asking; a start that asks for no protection is refused, and so is one on an account without a Zero Trust organization or a token without the Access permissions, with the words the Settings checks use.
- The Access placeholders are filled in on every install, update and settings change. An install protected from the start already has its audience tag at its first upload.
- An app whose entry lists public paths gets a second Access application, "Appflare: <app> (<Worker>) public paths", that keeps those paths public with a bypass policy on every address the app answers on: workers.dev while it is on, custom domains, and a wildcard domain's base and every name under it. It is brought in step when a domain is added or removed, when workers.dev is turned on or off, around updates and rollbacks, and when the install finishes, and is deleted before the app's own application when protection comes off or the app is uninstalled.
- External domains work with protection: a new one is covered by the app's Access application (and its public paths) before its custom hostname is made, under the Access lock so it cannot race turning protection on; a removed one loses its public paths first and its destination after the custom hostname is deleted. Health checks still never send the app's Access token to an external domain.
- Rolling back to a version whose entry requires protection is refused while the app is not protected, when the rollback starts and again in the job.
- Uninstalling a protected app deletes its public paths' Access application before any domain is released; if that fails the uninstall stops before anything is deleted. Removing a custom, wildcard or external domain stops, with the domain still attached, when its public paths cannot be taken off first.
- The catalog's `"access"` requirement is checked when protection will actually be on: an install the admin protects, or of an app whose entry requires protection, is refused before anything is created when the account has no Zero Trust organization or the token lacks the Access permissions. An entry that lists `"access"` without requiring protection installs unprotected on any account: its app page says Cloudflare Access is needed only if you protect the app (read from the Zero Trust probe of "What this account can run", shown quietly), and the requirement asks for no confirmation.
- Protection decisions read the catalog revision recorded for the installed release, not only the signed copy: whether protection may be turned off, which paths stay public, whether the app's settings use the Access values, and whether an update or rollback must wait for protection. A revision that changes a protected app's public paths marks its installs for the scheduled run, which brings their Access applications in step. The scheduled run also looks for newer revisions of protected apps' releases itself, at most seven installs a run in turn (a cursor in `settings`), through the same verified and cached path as the app's page, and resyncs a changed one in the same run; a fetch that fails is logged, never fatal.
- Revisions may narrow a protected app's public paths on their own but never widen them: each protected install records the public paths an admin accepted (a new `install_access.accepted_bypass_json` column, migration 0006, filled in for apps already protected from the paths they have now), set by installing the app protected, protecting it or protecting it again, an update, a rollback, and the new **Make public** action. Only paths the entry lists and an admin accepted are made public; a path the entry drops leaves the accepted list too. The app's Cloudflare Access card lists paths a revision added ("The catalog now lists /x/* as public."), with **Make public** for admins, which runs under the Access lock and then brings the Access applications in step.
- A revision that makes protection required for an app installed unprotected never protects it: the card shows a warning ("The catalog now says this app must run behind Cloudflare Access.") with **Turn on** for admins, and Home lists the app under Needs attention.
- The scheduled upkeep of protected apps runs as three `SELF` units, each with its own invocation and subrequest budget and one subrequest of the cron: catalog revisions (`refreshAccessRevisions`, seven installs a run), service tokens and the users policy retry (`renewAccessTokens`), and Access resyncs with the check that their applications still exist (`resyncAccessApps`, three resyncs and at most eight one-by-one reads a run). None runs while no app has an Access record; each reports failures as log lines without failing the run, and each stays within 42 calls at its bounds.
- **Make public** accepts only the paths the card showed that the entry still lists when the click arrives; a path a revision added after the page loaded keeps waiting and shows after the reload. Home's Needs attention check for apps whose entry now requires protection is one D1 query, whatever the number of installs.
- "What this account can run", Home and the catalog's app pages no longer count an app whose entry lists `"access"` without requiring protection as needing Zero Trust (from the index row's new `accessOffer`, or the catalog manifest), unless Appflare protects it; any protected install counts. The docs site's app pages say "Only if you protect it" for such an app.
- An update to a version whose entry requires protection is refused while the app is not protected ("This version must run behind Cloudflare Access. Turn protection on for the app first, then update."), when it starts and again in the job; automatic updates leave it for an admin.
- Updates and rollbacks take public paths the coming version drops off before it serves, and add its new ones once it is recorded. A rollback to a version whose settings use the Access placeholders and were deployed with another protection than the app has now deploys them again with the current values (a settings change started after it). Snapshots record the protection their version was deployed with.
- Removing a custom or wildcard domain, or turning workers.dev off, takes its public paths off before the address is released. A sync of a protected app's Access applications that fails outside a job is recorded on the install and tried again by the cron, three installs a run.
- Jobs that turn protection on or off are listed as "Cloudflare Access change".
