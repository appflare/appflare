Install from a repository. With sandbox builds on and the account on Workers Paid, admins see "From a repository" on the Catalog page: enter a public GitHub repository, optionally a branch, tag or commit and a build command, confirm the cost, and the sandbox Worker builds it. Appflare reads the repository's branches from GitHub first, so a private repository or a missing branch is refused before a container starts, and pins the build to that commit. The build's review page shows the source, what the sandbox Worker detected, the resources and bindings the install would create, the services it uses and whether the account offers them, and every reason the install would refuse it, in the install's own words (Hyperdrive, mTLS certificates, bindings to other Workers, Containers and other wrangler config sections Appflare cannot deploy). Installing runs the ordinary install job with the reviewed build as its artifact, read back and checked against its digest; nothing is built again. A build installs once and can be thrown away.

Such installs are recorded as coming from a repository, with the repository, the branch or tag and the commit, kept through updates, snapshots and rollbacks (new `installs` and `snapshots` columns, and a `source_builds` table). They are named `owner/repo`, marked "Not from the catalog, not checked" in the app list and on their page, are never matched with a catalog app of the same name, and are never updated automatically. Their page has "Check for changes", which reads the newest commit of their branch or tag, and "Rebuild and update", which builds that commit for review and then runs the ordinary update, asking for any secret the new build introduces.

A catalog app's page offers "Advanced: build from source at a commit", which builds the app's repository at another branch, tag or commit with the catalog's secrets, settings and build command, and lists the bindings that differ from the catalog's release. Such an install is marked "Built from source, not checked" and is not updated automatically; updating from the catalog puts the catalog's release back. Usage data records these jobs' kind, where the app comes from, and how they ended, never the repository.
