Installed apps can now be protected with Cloudflare Access from the manager's pages.

- The install form has **Protect with Cloudflare Access** under the address. It starts off, on when the app's catalog entry recommends it, and on and fixed when the entry requires it. It says who gets in (every Appflare user, members included, with the count), how they sign in (the Zero Trust organization's login methods, and that each person must be able to sign in with the email of their Appflare account), and what stays public: the entry's public paths, or a sentence that everything at the app's addresses asks for a sign-in, shared links included. While the account cannot protect apps (no Zero Trust organization, or a token without an Access permission) it is off and disabled, with the reason and a link to the row of What this account can run that fixes it; an app that requires protection waits for the fix. Apps deployed by their own installer are not offered it.
- The app's Domains and email tab has a **Cloudflare Access** card: whether the app is protected, who gets in, its public paths, its Access application with a link to the Zero Trust dashboard, and a note when a sync of its Access applications failed (Appflare tries again; the addresses stay protected). Admins turn protection on or off after a confirmation that says what happens; each starts the settings change job and opens its log. "Protect again" is offered, with a line saying why, only when Appflare's records show something to repair: the app's Access application (or the one keeping its public paths open) was deleted in Cloudflare, the "Appflare users" policy was made again or is missing, the record of the app's Access application is incomplete, or its last sync failed. It is offered for apps whose entry requires protection too. Each protected app now records which "Appflare users" policy its application names (a new column, filled in for apps already protected), which is how a policy made again is told apart.
- While any app is protected, the scheduled run makes two more Cloudflare reads: one listing of Access applications, marking an app whose application is gone (and unmarking one found again), and one read of "Appflare users", which it makes again when it was deleted, so every protected app then asks to be protected again. A refused or failed read is logged and never fails the run; protecting an app clears its mark. An app whose entry requires protection has no off control. Members see the state.
- A single quiet line says so when Appflare has more users than Zero Trust Free covers (50).
- Login methods are named without repeating themselves: a provider's own name is shown only when it adds something ("GitHub (work)", "Google: Company SSO"), never "One-time PIN (a code sent by email): One-time PIN".
- The catalog's **Cloudflare Access** requirement reads better and links to the new docs page on protecting apps.
