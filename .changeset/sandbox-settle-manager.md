Sandbox runs no longer start while the sandbox Worker is still rolling out a new version. Every secret stored on the sandbox Worker deploys a new version of it, and a new version resets the containers it runs, so a self-deploying install used to cut off its own installer run as it started. Before a build or an installer run, the job now asks the sandbox Worker which version answers until the version Cloudflare lists as deployed has answered three times in a row (or, when the deployments API answers 429 or 5xx or traffic is split, the same version has), for about a minute at most; past that it logs a warning and starts the run anyway. The job log says which way it waited. The waiting runs as a job unit over the manager's `SELF` binding, so it costs the job one subrequest; a manager without that binding asks at most 10 times, without retrying. This covers the job's own writes and a token or secret entered on the install page just before the job. When Workflows runs a secret step again after it finished, the step no longer stores or deletes the secret a second time (each write deployed yet another version of the sandbox Worker) or logs it twice: an install logged "Stored ... on the sandbox Worker" twice, and an uninstall logged a secret as deleted and then as no longer there.
