Apps of several Workers can give each Worker its own value of a secret name: the install form, the update form and the app's settings ask for each such secret on its own, the install job, updates and settings changes set each on the Workers that read it, and the install records it by its key with the name the Worker reads (installs made before keep their records as they are, since a secret without a key is known by its name). A rollback settles each Worker's secret records against the version it serves again, reading the secrets of every other Worker that has its own, and re-creates a record under the secret's key. Removing a secret the installed version no longer declares never deletes a value the Worker reads for a declared secret of the same name, and an update that gives a secret a new key keeps the value the Workers already have instead of asking for it again. Changing the app's address deploys the settings again when a service binding's props use it, and the vars a catalog entry's config patches set show read-only in the app's settings with the technical names. Service bindings with `props` are uploaded with them, the placeholders in their strings filled in as in vars (`{{appUrl}}` and the rest), on install, update and settings changes. The catalog's `requires` values `secret-keys`, `service-props` and `config-patch-values` are features of this manager, so they are never shown or asked to be confirmed as something the account needs.
