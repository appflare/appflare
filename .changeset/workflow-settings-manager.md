Create and update an app's Workflows with the settings its wrangler config gives them: the most steps an instance may run, how many instances run at once, the schedules that start one, and how long successful and failed instances are kept. Installs send them when they create each Workflow, and updates, rollbacks and the scheduled repair send those of the version they deploy or find installed. Cloudflare puts a limit, concurrency or retention a version leaves out back to its default, and a version without schedules is sent with an empty list of them, so no schedule of an earlier version stays. When an update or rollback deploys a version that no longer defines a Workflow an earlier version ran on a schedule, the Workflow stays until the uninstall but its schedule is taken off, since each run would fail on a class the version lacks; the job log says so, and warns with what to do when Cloudflare refuses or keeps the schedule. When Cloudflare refuses a Workflow, the job log names the settings it was asked for (Workers Free takes at most 1,024 steps and 100 instances at once, and no schedule), and a refused schedule now reads as one sentence.
