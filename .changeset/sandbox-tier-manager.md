Install and update `sandbox` tier apps, which have no prebuilt release, by building them in the account's sandbox Worker. Settings has a Sandbox builds card that shows whether the manager is connected, how to enable the sandbox Worker with the CLI, and a "Connect sandbox builds" action that adds the `SANDBOX` service binding by creating a version of the running manager with only that binding added, checking its preview, and deploying it; self-updates keep the binding while the sandbox Worker exists and add it when it appeared. The catalog shows a "Built in your account" badge and each build's container size and cost; the install form and the update dialog ask the admin to confirm that cost. The install and update jobs build the pinned commit in a `build in sandbox` step, read the result through the binding with range requests, and accept its unsigned manifest only when its digest, commit, app, version and catalog manifest match. The job page shows the build's live output, the app page shows where and from which commit and image the app was built, uninstalls delete the install's builds, and updates keep only the current and previous build. The database records each install's and snapshot's build provenance and, for each resource, whether Appflare or the app's own installer manages it. A catalog index entry this manager cannot read is now left out, logged, and counted on the catalog page instead of making the whole catalog unavailable.
