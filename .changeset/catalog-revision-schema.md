A catalog manifest can carry `revision`, a whole number from 1 (1 when omitted), so an edit of an already released version's form or copy can be published without a new build. A revision may change only `REVISABLE_CATALOG_FIELDS` (`name`, `summary`, `homepage`, `license`, `categories`, `authors`, `maintainers`, `secrets`, `vars`, `postInstall`, `bump`); everything else describes the build or what an install provisions and still needs a new pin. Index rows gain `revision` and, for an artifact tier row whose revision is above its release's, `catalogManifest`: the URL, sha256, `keyId` and base64 Ed25519 `signature` of the revised manifest, signed with the release's key because its var defaults and generated secrets reach the Worker. Both fields are optional, so older indexes still parse. New helpers: `catalogRevision`, `catalogFieldChanges`, `catalogRevisionProblem`, `revisedArtifactProblem` (also checks the revised vars against the signed Worker), `withRevisedCatalog`, and `verifySignature`, the Ed25519 check `verifyManifestSignature` now uses, for bytes whose key id is given separately. The field is optional rather than defaulted, so manifests and artifacts written before it parse to the same shape and publish the same bytes.
