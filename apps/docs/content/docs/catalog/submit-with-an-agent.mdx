---
title: Package an app for the catalog with an AI agent
description: A prompt for your coding agent. It writes the app's appflare.jsonc, checks it with the catalog's tooling, and opens the pull request.
---

Adding an app to the catalog takes one file, `apps/<slug>/appflare.jsonc`, in a pull
request to [appflare/catalog](https://github.com/appflare/catalog). A coding agent that
runs commands on your computer, such as Claude Code, Codex, Cursor, or Gemini CLI, can
read the app's repository, write that file, run the catalog's checks, and open the pull
request. [Submit an app](/catalog/submit/) describes the same process by hand.

Copy the prompt below, replace the two placeholders on its first lines, and paste it
into the agent. It needs Node.js 22, pnpm, git, and the GitHub CLI (`gh`). It needs no
Cloudflare credentials: packing an app never touches an account.

<Callout title="For people with access to appflare/appflare, until launch">

The catalog's tooling is built from the appflare/appflare repository, which is private
until launch, so the prompt only works for people who can clone it. For the same
reason a pull request from a fork fails the catalog's `verify` check until that
repository is public.

</Callout>

What stays with you:

- logging in to GitHub with `gh auth login`, if you are not logged in yet;
- approving the push and the pull request, after reading the manifest;
- the review on the pull request. As a maintainer of the entry, you are also asked to
  review its [version bumps](/catalog/bumps/) later.

## The prompt

<Prompt>

```text title="Prompt"
Help me add an app to the Appflare catalog: write its catalog manifest, check it with the catalog's own tooling, and open a pull request.

The app's repository: <UPSTREAM REPOSITORY URL>
My GitHub username (the entry's maintainer): <MY GITHUB USERNAME>

Read these first. Where they disagree with this prompt, they win:
- CONTRIBUTING.md of https://github.com/appflare/catalog
- https://appflare-docs.appflare-dev.workers.dev/catalog/submit.md
- https://appflare-docs.appflare-dev.workers.dev/catalog/manifest-reference.md

Rules for this whole session:
- The entry is one new folder, apps/<slug>/, plus the regenerated CODEOWNERS. Never change the app's own repository, other apps' folders, index.json, schema/, or the workflows. Never sign, release, or publish anything.
- Never print, paste, or ask me for a token. No Cloudflare credentials are needed.
- Ask me before anything that pushes to GitHub or opens a pull request.

Steps:

1. Check that the app qualifies. If it does not, stop and tell me why.
   - A public GitHub repository with a license.
   - Not a proxy, tunnel, or circumvention tool.
   - It deploys with wrangler: it has its own wrangler config (wrangler.jsonc, wrangler.json, or wrangler.toml).
   - It is self-contained: its own Worker defines its Durable Objects and Workflows, and its only service binding, if any, points at its own Worker.
   - No Hyperdrive or mTLS certificate bindings; the catalog's install check does not support them yet.
   - If it has no wrangler project Appflare can read (it ships its own installer) or must be built in each user's account, read the sandbox and self-deploying tier sections of CONTRIBUTING.md and ask me before going on. Those tiers need Workers Paid.
2. Run `gh auth status`. If I am not logged in, ask me to run `gh auth login`. Ask me before forking. Then fork and clone the catalog with `gh repo fork appflare/catalog --clone`, and create a branch named add-<slug>.
3. Set up the catalog's tooling, as CONTRIBUTING.md describes. Clone https://github.com/appflare/appflare next to the catalog checkout as ../appflare (the repository is private until launch: use `gh repo clone appflare/appflare ../appflare` with my gh login, and if I have no access, stop and tell me), then, in the catalog checkout:
     git -C ../appflare checkout "$(cat .appflare-ref)"
     (cd ../appflare && pnpm install --frozen-lockfile && pnpm build)
     pnpm install
4. Choose the slug: short, lower case, the app's usual name, not already used in apps/. Pin the version: if the repository has stable semver tags, take the newest one; source.ref is the tag and source.sha the full 40-character commit it points to (for an annotated tag, the commit, not the tag object). Otherwise take the head of the default branch, with source.ref set to the branch name. When the tags do not describe this app, as in a repository of many templates, also set install.version.
5. Write apps/<slug>/appflare.jsonc, starting from a copy of apps/cut/appflare.jsonc. Read the app's wrangler config, README, .dev.vars.example if there is one, and the code that reads env. Fill in:
   - $schema, slug, name, summary (one sentence), homepage (https), repo (owner/name), license (as upstream states it), categories.
   - authors: who wrote the app upstream, as the repository owner, its README, or its license names them. Each is { "name", "url"?, "github"?, "x"? }, with handles written without @.
   - maintainers: [<MY GITHUB USERNAME>].
   - install: tier "artifact"; packageManager from the app's lockfile; wranglerConfig, the path of the app's own wrangler config (never a config a build generates); workerName, the config's name. Only when needed: buildCommand, a single command without shell syntax (or a list of such commands run in order, when the build has several steps or relies on a prebuild hook, which does not run), when the app needs a build step before wrangler deploy and its wrangler config has no build.command; healthPath, when / returns an error or needs a login; healthMode "status-only", when every route sits behind a login or Cloudflare Access; fixedWorkerName, when the app only works under one Worker name.
   - plan: "paid" when the Worker is larger than 3 MB compressed or needs paid features, otherwise "free".
   - requires: the account features it needs beyond Workers (r2, workers-ai, zone, email-routing, browser-rendering, containers, analytics-engine).
   - secrets: every secret the app reads that its wrangler config does not set, each with a label and help text; "generate": true for passwords and keys the user does not need to choose. When the app wants a bcrypt hash of a password, list the password and the hash, the hash with "derive": { "from": "<password secret>", "method": "bcrypt" }.
   - vars: settings an admin should set or change. Use {{workerUrl}} or {{workerName}} where the app needs its own URL or name, and {{accountId}} where it needs the Cloudflare account id.
   - postInstall: what to do after installing, in Markdown ({{workerUrl}} works).
   - tokenPermissions: only if the app calls the Cloudflare API with a token of its own.
   - resources.vectorize: dimensions and metric for each Vectorize binding.
   Do not repeat bindings, compatibility settings, static assets, cron triggers, or migrations; the packer reads them from the wrangler config at the pin.
6. Check the entry, in the catalog checkout:
     pnpm validate <slug>
     pnpm pack-app <slug>
     pnpm gen-codeowners
   pack-app clones the app at the pin, installs its dependencies with install scripts disabled, and runs its build on this machine without credentials. It prints the Worker's module count, which must be 21 or fewer. If it is higher, or the build fails, stop and tell me what the app would need to change. Do not commit the dist/ directory pack-app writes.
7. Commit apps/<slug>/ and CODEOWNERS with the message `feat(apps): add <slug>` and a body that says what the app is and why it belongs in the catalog. Check it with `pnpm exec commitlint --from origin/main`.
8. Show me the manifest and ask me to confirm. Then push the branch to my fork and open the pull request with `gh pr create --repo appflare/catalog`. In its description, say what the app does, which tag or commit it is pinned to, what validate and pack-app reported, and anything you were unsure about.

End with the pull request's URL and a list of what is left for me. Pull requests from forks get no CI secrets, so they fail the catalog's verify check until the appflare/appflare repository is public; if the pull request comes from a fork, say so in that list.
```

</Prompt>

## After the pull request

The catalog's checks and review work as for any other entry: see
[Open a pull request](/catalog/submit/#2-open-a-pull-request) and
[After merge](/catalog/submit/#after-merge). Every field of the manifest is described
in the [manifest reference](/catalog/manifest-reference/).
